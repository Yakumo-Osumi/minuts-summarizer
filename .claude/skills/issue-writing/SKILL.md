# Issue Writing

会話の内容から、GitHub Issue（タイトル＋本文）を `gh issue create` にそのまま渡せる形式で下書きする。このSkillは下書きまでを担い、ユーザーが明示的に承認するまでIssueを作成しない。

## 下書き前に

軽く重複チェックを行う：タイトルやキーワードが近い既存Issueがないか検索する（例：`gh issue list --search "<キーワード>"`）。これはブロッキングしない確認であり、似たものが見つかっても下書き自体は作成し、その旨を一言添えるに留める。

## 構成

本文は次の2セクションのみで構成する：

```markdown
## 背景

{何が問題か、なぜこのIssueが必要か}

## やること

- [ ] {具体的な作業項目}
- [ ] {具体的な作業項目}

完了基準：{どうなったら完了とみなすか。1行}
```

- これ以外のセクション（概要／現状／関連ファイル／補足など）は追加しない。この2見出し＋完了基準1行のみに留める。
- ラベル付けはスコープ外。ラベルの提案・付与は行わない。

## 「背景」の書き方

主に会話内容から組み立てる。裏付けとして有効な場合は、具体的なコード参照（例：`useSummarize.ts:15`）を含めてよい。行番号は「下書き作成時点のスナップショット」として扱い、その後のマージやリファクタリングでズレることは許容する。

このIssueが他のIssueやPRでの議論から派生したものである場合は、「背景」内に `関連: #N` の参照を追加する。`close`/`closes`/`fixes` などのキーワードでリンクしてはいけない。これらはマージ時の自動クローズを発動させるため、この程度の緩い関連付けには適さない。

## 「やること」と完了基準の書き方

「やること」は具体的な作業項目のチェックリストとする。末尾に、Issue全体としての完了基準を1行だけ明記する。第三者がどうなれば完了と判断できるかを、実際の検証方法に合わせて書く：

- 見た目・UIに関する作業や、ユーザーに見える挙動のバグ修正 → 人間が実際に操作して目視確認する必要がある旨を明記する
- ロジック・API・バックエンド寄りの作業 → 具体的な入出力やテストで判定できる基準を明記する
- 両方にまたがる場合 → その1行の中で両方の検証方法を併記する

## タイトル

既存の慣習に従う：conventional commit風のprefix（`feat:` `fix:` `chore:` `docs:` など）＋簡潔な日本語の要約。変更内容からprefix案を提示するが、必ずユーザーに確認を取る（`feat`と`fix`の境界は本質的に曖昧なことが多いため）。

## 下書きの提示

タイトルと本文は会話内にそのまま提示する。ファイルへの書き出しは行わない。ユーザーが明示的に承認した（必要に応じてタイトル・本文を調整した）後にのみ、以下を実行する：

```bash
gh issue create --title "<タイトル>" --body "<本文>"
```

ユーザーの明示的な承認前に `gh issue create` を実行してはいけない。
