# タスク抽出 評価ログ（results.md）

Task B: タスク抽出の精度評価（再現率・適合率・deadlineAccuracy）の記録。
各ラウンドで「何を変えたか」「なぜか」「結果どうなったか」を残す。

---

## 評価設計の初期決定（ADR 0002）

- `run-eval.ts` の新規作成（コミット `08e3e84`、2026-07-30）にあわせて、
  タスクマッチング方式の意思決定を `docs/adr/0002-task-eval-matching-strategy.md` として記録。
  採用したのは、assigneeの一致と、goldタスクに人手で付与したmatchKey（名詞・動詞）が
  output.contentに含まれるかどうかで判定する方式。

**検討したが却下した案（ADR 0002 Considered Options より）**

- 文言の完全一致でマッチング → AIの言い換えで必ず不一致になるため却下。
- 埋め込み/LLMによる意味的マッチング → 「評価は保存済み出力に対して行い、ライブAPI呼び出しに
  依存しない」「線引きの判断はAIに任せず本人が行う」という評価方針（issue #25背景）に反し、
  再現性も失われるため却下。
- deadlineの一致もマッチング成立条件に含める（厳密一致） → タスクを発見できたかという失敗モードと、
  deadlineを正しく抽出できたかという失敗モードが同じ指標に混ざり、誤り分析がしづらくなるため却下。

## v1（初回計測）

- 再現率 62.5% ／ 適合率 55.6% ／ deadlineAccuracy 60.0%（sample1〜3、マイクロ平均）

**原因分析**

- プロンプト（`deadline: 記載なければ未定`）と labeling-rules.md（期限なしは除外）の方針が矛盾しており、
  ツールが期限未定タスクを出力 → gold に無いため誤抽出（FP）として適合率を下げていた。
- sample2「担当は次回までに決める」を FN として検出。原因は、当時のルールが
  「相対期限（次回までに）」と「決定タスク（〜を決める）」の扱いを明文化していなかったこと。

**対処**

- プロンプトとルールの期限方針を統一（期限なしは除外で統一）。
- labeling-rules.md に「相対期限も期限として認める」「意思決定自体もタスクに含める」を追記。

## v2（方針統一後）

- 再現率 87.5% ／ 適合率 87.5% ／ deadlineAccuracy 100%（sample1〜3、マイクロ平均）

**原因分析（残差）**

- sample2 で FN/FP が対発生：gold「SNS投稿案を3案**用意する**」 / output「3案**作成する**」。
  担当・対象・期限は完全一致だが、動詞の表記差で matchKey が不一致と判定していた。
  → **ツールの誤りではなく、評価器（matchKeyの動詞照合）の脆さ**と判断。

**対処**

- matchKey から動詞（verb）の照合を除外し、「担当者＋名詞（noun）」でマッチさせる方式に変更。
- sample1〜3 は全指標 100% に到達（※調整データでの100%であり、実力の証明ではないことに留意）。

## 評価汚染の防止（プロンプト内の例の中立化）

- SYSTEM_INSTRUCTION 内の具体例（"夏季の一斉休業"、"MTG"、"8月5日" 等）が
  sample1・sample3 の本文と一致しており、除外判定の"答え"を教えてしまっている状態だった。
- 全ての例を、評価サンプルに登場しない中立な題材（サーバー移設、創立記念日 等）に差し替えた。

## holdout 初回計測（未調整データでの実力測定）

- holdout1：再現率 33.3% ／ 適合率 50.0% ／ deadlineAccuracy 100%
- holdout2：再現率 66.7% ／ 適合率 66.7% ／ deadlineAccuracy 50.0%
- 合計（マイクロ平均）：再現率 50.0% ／ 適合率 60.0% ／ deadlineAccuracy 66.7%

**原因分析**

1. holdout1「藤井/返信テンプレートの見直し」が FN と FP に同一内容で計上 →
   gold の matchKey.noun 設定ミス（コピペ残り）による評価バグ。ツールは正しく抽出できていた。
2. holdout1「不明/満足度アンケートの担当を決める」が FN → 本物の見逃し。
   ルールに「担当者不明でもタスクに含める」という**含有の許可**が明記されておらず、
   モデルが担当未定タスクを暗黙に除外していた。
3. holdout2「送料改定のお知らせページ」で FN/FP 対発生 → matchKey.noun に格助詞（の）が
   含まれており、output側の表記（送料改定**の**お知らせページ）との部分一致に失敗。評価器の脆さ。
4. holdout2 deadline「今月末まで」→ 出力が「8月31日」という**誤った月**になった（1回のみ観測）。
   複数回再試行では「11月30日」（正）で安定 → **モデルによる相対日付計算の低頻度な非決定性**を確認。

**対処**

- matchKey.noun のコピペミスを修正。
- labeling-rules.md エッジケース#1「担当者不明はタスクに含める」ことを明記。
- matchKey の照合前に格助詞（の・を・が・は・に・で 等）を除去する正規化処理を run-eval.ts に追加。
- deadline 比較前に日付表記（07月17日 / 7月17日 等）をISO形式へ正規化する処理を追加。
- 相対期限の表記ゆれ（"次回" / "次回まで" 等）を標準形に丸める正規化を追加。
- 相対日付の計算リスクについては、エッジケース#4（基準が分かれば変換する）を維持する判断とした。
  低頻度の計算ミスの可能性は残るが、実用性を優先。

（追記）上記のうち matchKey.noun の格助詞ゆれ対応（コミット `21eb52b`、2026-08-16）では、
run-eval.ts の正規化処理に加えて、labeling-rules.md に「matchKey（評価用）の設計方針」節を
新設し、matchKey.noun の命名方針を明文化した：

1. そのタスクを一意に特定できる最短の名詞の核を選び、格助詞を含まない形にする。
2. 短くしすぎて別タスクと衝突する場合は、衝突しない範囲で最小限の語を追加する。
3. run-eval.ts側の正規化は保険であり、命名方針に沿って書くことを基本とする。

## holdout 追加の見逃し対応

- 修正後も holdout1「満足度アンケートの担当を決める」の deadline が「次回まで」のまま
  変換されず FN として残存。
- 原因：基準日（「次回のサポート定例は10月14日」）が、対象の文から離れた
  「その他」セクションに記載されており、プロンプトが「本文全体を横断して基準日を探す」ことを
  明示していなかった（近接した文脈のみ拾う傾向があった）。複数回再実行しても一貫して
  同じ結果になることを確認し、非決定性ではなく構造的な指示不足と判断。

**対処**

- labeling-rules.md / SYSTEM_INSTRUCTION のエッジケース#4に、
  「基準日は当該の文の近くだけでなく、議事録全体（離れた箇所も含む）から探すこと」を追記。

（追記）この「次回まで」未変換の実出力は、直前のコミット `4417ba1`（2026-08-16）で
holdout1・holdout2 を実際にAPI再実行して得られたfixture差分から判明したもの。
同コミットでは、この見逃しの発見と合わせて以下2点も修正されている：

1. 「タスクに含めるもの」項目とエッジケース#4で、相対期限の変換ルールが重複定義（内容が
   微妙に食い違う形で二重に書かれている状態）になっていたため、エッジケース側に一本化。
2. 変換した絶対日付に「まで」等の助詞が残ってしまう不具合（例：「2026年10月14日まで」と
   出力される）を実際の出力で確認し、「日付を出力したものは助詞を付けない」というルールを
   エッジケース#5としてSYSTEM_INSTRUCTION・labeling-rules.md双方に明記。

## 既知の限界（今後の課題）

- matchKey は「担当者＋名詞」のみで照合しており、動詞（行動の種類）を見ていない。
  同一担当者・同一対象で異なる行動を取るタスクが複数ある場合、誤マッチの可能性が残る
  （現状のサンプル規模では未発生）。
- 相対日付の計算をモデルに行わせている箇所（エッジケース#4）は、低頻度ながら
  計算ミスの実例（8月31日の誤答）を観測済み。将来的にはコード側（JavaScript）での
  決定的な日付計算への切り替えを検討する余地がある。
- matchKey.noun の選定基準（最短の核を選ぶ）は人手判断に依存しており、
  選定を誤ると再現率・適合率に直接影響する。

## 自己診断メモ（Task Bの目的）

- matchKeyのラベル付けでは、例えば「FAQページの料金記載を更新する」という文があった場合、「FAQページ」と「料金記載」のどちらを選ぶか、それとも両方選ぶかというところから悩んだ。固有名詞であるFAQページの方が良いとすぐに判断できたため、この判断自体には特に消耗しなかった。
- 評価においては、FNの方がFPより原因の特定が難しかった。FPはツール側の文言が明らかに不明確なケースが多く原因を特定しやすかったが、FNは具体的な事例を丁寧に洗い出さないと対策できなかったためだ。
- 一番詰まったのはdeadlineの線引きだ。相対期限で期限が不明確なものはそのままの言葉（「次回まで」など）を使う方針にしたため、日付と「まで」が重複して出力されてしまう不具合が起き、ツール側の調整に苦労した。
- 一番手応えがあったのは、holdoutの評価を全て100%にできたときだ。
- 地道な検証作業には達成感はあったが、得意とは言えない気がする。タスクを作成してから完了まで1ヶ月かかっており、本当に楽しいならもっとコミット頻度が上がっているはずだからだ。ただ、今回のようにholdoutでの100%達成という明確な区切りを目標に設定すると、最後までやり切れることも確認できた。今後はこの手の地道な作業には、小さなマイルストーンを意図的に設定して取り組みたい。
