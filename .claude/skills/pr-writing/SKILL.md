# PR Writing

現在のブランチの変更内容から、PR説明（タイトル＋本文）を `gh pr create` にそのまま渡せる形式で下書きする。このSkillは下書きと、承認後の作成（push + PR作成）までを担う。

## 下書き前に

このブランチに既にPRが存在しないか軽く確認する（例：`gh pr list --head <branch名>`）。これはブロッキングしない確認であり、既存PRが見つかった場合は「新規下書きにするか、既存PRの更新にするか」をユーザーに確認するに留める。

## 変更内容の取得範囲

ベースブランチ（`gh repo view --json defaultBranchRef` や `git symbolic-ref refs/remotes/origin/HEAD` で自動検出。不明なら `main`）から現在のブランチが分岐した後の全commitを対象にする：

```bash
git log <base>..HEAD
git diff <base>...HEAD
```

直近1commitや直近N件ではなく、分岐後の全体を見る。PRはブランチ単位のレビュー対象であり、一部だけを見ると変更内容や概要が欠落するため。

## 構成

本文は次の3セクションを核とする：

```markdown
## 概要

{このPRが何を・なぜ行うかの要約}

## 変更内容

{変更点の一覧。ファイル単位・機能単位など変更の性質に応じて箇条書きや表でまとめる}

## テスト計画

- [x] {実際に確認した内容}
- [ ] {未確認の項目（正直に未実施と書く）}
```

この3つは必須。加えて、内容上必要な場合に限り「設計上の判断」「既知の制限・残作業」などの任意セクションを追加してよい（過去のPR #1, #3 で採用された構成）。不要な情報を埋めるためだけにセクションを増やさない。

## 「概要」の書き方

会話内でのやり取りと、取得したgit log/diffから組み立てる。何を実装したか、ではなく「なぜこの変更が必要か」を中心に書く。

## 「テスト計画」の書き方

`/verify` skillと連携する：このセッション内で実際に確認した動作（手動操作・curl実行・ブラウザ確認等）だけをチェック済み（`[x]`）として記載し、確認していない項目は未実施（`[ ]`）のまま正直に書く。確認していないことを確認済みであるかのように書いてはいけない。

## 関連Issueの扱い

- **ブランチの発端となった元Issue**：会話内で明示的に言及されている場合のみ、本文冒頭に `close #N` を1行追加し、マージ時に自動クローズさせる。
- **作業中に発見・新規作成した別Issue**（元Issueとは別件のレビュー指摘や技術的負債など）：PR本文では一切参照しない。close/closes/fixesはもちろん、「関連: #N」のようなソフトな参照も行わない。将来別のブランチ・PRで対応する運用のため。
- 該当Issueの探索は会話内で既に言及された番号を拾うだけに留める。`gh issue list` 等で自動検索はしない。判断に迷う場合はユーザーに確認する。

## タイトル

conventional commit風のprefix（`feat:` `fix:` `chore:` `docs:` など）＋簡潔な日本語要約とする。prefixのルールは `CONTRIBUTING.md` の「コミットメッセージ規則」に既に定義されているため、ここでは重複させず、その表を参照する。変更内容からprefix案を提示するが、必ずユーザーに確認を取る。

## 下書きの提示

タイトルと本文は、デフォルトでは会話内にそのまま提示する。ファイルへの書き出しは行わない。

ユーザーが明示的に「ファイルに残したい」等を依頼した場合のみ、スクラッチパッドディレクトリに下書きファイルを作成する。リポジトリ内には残さない。

## 作成の実行

ユーザーが明示的に承認した（必要に応じてタイトル・本文を調整した）後にのみ、以下を実行する：

```bash
# 未pushの場合のみ
git push -u origin <branch名>

gh pr create --title "<タイトル>" --body "<本文>"
```

ユーザーの明示的な承認前に `git push` や `gh pr create` を実行してはいけない。
